# Translator Module Overview

This document explains the purpose, inputs, outputs, and data flow of the various components inside the `translator_module`. It also maps these components to the requirements specified in the `Minor Project Description ( Extended ).pdf`.

## 1. Modules Created

The `translator_module` is divided into three main areas: the CLI entry point, the `rag` (Retrieval-Augmented Generation) package, and the `agent` package.

### CLI Entry Point
- **`cli.py`**
  - **Description**: The interactive shell that wraps the entire translation pipeline. It initializes the system and provides a prompt for users to type their questions.
  - **Input**: User queries from the terminal (plain English).
  - **Output**: The generated `OksQuery` string, intermediate representation (IR), and an explanation printed to the console.

### RAG Package (Schema Discovery)
- **`rag/ingest.py` (HybridIndexer)**
  - **Description**: Responsible for parsing the raw OKS schema XML file, chunking the classes and attributes, and building a hybrid search index (Vector embeddings via FAISS + Keyword search via BM25).
  - **Input**: OKS schema XML file path.
  - **Output**: An in-memory searchable index of the OKS schema.

- **`rag/retrieve.py` (Retriever)**
  - **Description**: Performs the actual search against the `HybridIndexer`. It takes the user's question and finds the most relevant schema classes and attributes.
  - **Input**: Plain English search query string.
  - **Output**: A list of relevant schema fragments (text blocks) to be fed into the LLM.

### Agent Package (Translation & Validation)
- **`agent/translator.py` (OksTranslator)**
  - **Description**: The core orchestrator. It ties together the schema retriever, the few-shot examples, and the LLM API to generate the query.
  - **Input**: Plain English question (from `cli.py`).
  - **Output**: A dictionary containing the final `oks_query` string, the `ir` JSON object, and an `explanation`.

- **`agent/few_shot.py` (FewShotManager)**
  - **Description**: Loads and formats a dataset of known good question-to-query pairs.
  - **Input**: Path to a `.jsonl` file containing ground-truth queries.
  - **Output**: Formatted prompt string of few-shot examples to guide the LLM's output.

- **`agent/ir_validator.py` (validate_ir)**
  - **Description**: Uses Pydantic models to strictly validate the JSON Intermediate Representation (IR) generated by the LLM to ensure it conforms to the expected structure.
  - **Input**: Raw JSON dictionary from the LLM.
  - **Output**: A validated `QueryIR` Python object. Raises a `ValidationError` if the LLM hallucinated bad syntax.

- **`agent/serializer.py` (serialize_ir_to_oks)**
  - **Description**: Takes the validated Python object and recursively formats it into the highly specific, LISP-like `OksQuery` string syntax.
  - **Input**: Validated `QueryIR` object.
  - **Output**: The final `OksQuery` string.

## 2. Data Flow

The translation process follows a strict pipeline:

1. **User Input**: The user types a question like *"Find all computers running application X"* into `cli.py`.
2. **Context Gathering**: `OksTranslator` asks `Retriever` to find the relevant schema parts for this question (e.g., the `Computer` and `Application` classes).
3. **Prompt Construction**: `OksTranslator` combines the user's question, the retrieved schema context, and examples from `FewShotManager` into a single prompt for the LLM.
4. **LLM Generation**: The LLM processes the prompt and outputs a structured JSON object called an Intermediate Representation (IR).
5. **Validation Loop**: The IR is passed through `validate_ir` (`ir_validator.py`).
   - *If invalid*: The validation error is caught, and (in a full loop) could be sent back to the LLM to self-correct.
   - *If valid*: It becomes a `QueryIR` object.
6. **Serialization**: `serialize_ir_to_oks` (`serializer.py`) converts the `QueryIR` object into the final `OksQuery` syntax string.
7. **Output**: `cli.py` prints the final query and explanation to the user.

## 3. Satisfied Requirements

Based on the **"Configuration Online Service — Modules & MCP Server"** PDF specification, the current `translator_module` satisfies the following deliverables:

### ✅ M2. Schema Discovery
**Status:** Satisfied by the `rag` package.
**Details:** The `rag/ingest.py` and `rag/retrieve.py` modules successfully handle the requirement that OKS has "too many [classes] to give an LLM all at once" by finding "just the part of the schema relevant to a given question."

### ✅ M3. Text-to-OksQuery Translation
**Status:** Satisfied by the `agent` package.
**Details:** The `agent/translator.py` module successfully turns a plain-English question into a valid `OksQuery` string.
- It uses the schema piece from M2.
- It uses few-shot examples via `few_shot.py`.
- It implements the required "validate/repair loop that catches bad queries before running them" via `ir_validator.py` and the Intermediate Representation pattern.

### 🚧 M8. MCP Server Shell
**Status:** Partially Satisfied / Foundation Laid.
**Details:** The project requires connecting the modules together as tools an LLM can call. `cli.py` currently connects M2 and M3 together into a working agent shell, though it is exposed as a terminal CLI rather than a formal MCP (Model Context Protocol) server.

### Unimplemented Modules
The following modules from the specification are not yet implemented in this repository:
- **M1:** Run/Revision Resolver
- **M4:** Query Execution & Formatting
- **M5:** Object Lookup
- **M6:** Relationship Navigation
- **M7:** Revision Diff/Comparison
